Proposed Solution

3.1 Platform Architecture

We are building this as a Bun-powered monorepo that houses the web application, mobile app, backend API, background workers, and shared packages (types, UI components, utilities, integration adapters) in a single clean workspace. There is one unified web app with role-based access control — every user role (Super Admin, Director, Sales Manager, Agent, Finance, Site Engineer, Channel Partner) logs into the same application and sees only what their role permits.

Why a monorepo? Because when your lead scoring logic lives in one package, and the same logic gets used by the web app, the mobile app, and the WhatsApp drip worker, you do not want three copies drifting out of sync. One source of truth, strongly typed end-to-end, with Bun's speed advantage on install times and script execution.

Why Bun? Faster installs, faster test runs, native TypeScript execution without a separate build step, and first-class monorepo support. For a project with a tight timeline, the developer-velocity gains compound every day.

3.2 Technology Stack

Area Technology
Frontend (Web App + Mobile App) React 19, RTK Query, TypeScript, Tailwind CSS, Shadcn/ui, React Hook Form + Zod, TanStack Table, React Native (mobile)
Backend (API & Services) Node.js, Express (MVCS pattern), TypeScript, Zod for runtime validation
Database & Data Layer PostgreSQL, Prisma ORM, Redis
Background Jobs BullMQ on Redis (webhook processing, drip sequences, demand letter generation, reconciliation)
Monorepo Tooling Bun workspaces, shared packages for types/UI/integrations
Infrastructure Dockerized services, GitHub Actions CI/CD, Cloudflare CDN + WAF

3.3 Third-Party Integration Layer

Every external system sits behind a versioned adapter in a shared integrations package. This matters because these portals change their APIs regularly — when MagicBricks changes their webhook schema next year, we change one file, not fifty.
